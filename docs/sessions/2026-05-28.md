## 1. Game-Over 3D Text + Background Fade

**Commit:** `e146e0e` — feat: game-over 3D text, background fade, unified title colors

### What we built
When a match ends, a large 3D text message fades in above the cube — "X WINS!", "O WINS!", or "DRAW!" — each letter using the same rainbow color palette as the title. Simultaneously, the scene background fades from its normal color to a deep purple-navy (`#141425`), creating a "cinematic end" feel. On Reset or Next Round, both the text and the background return to normal.

### The game-over text system (title.js)

**The core problem:** Three.js `TextGeometry` is async — you can't build it until the font file has loaded from the network. So `showGameOver(text)` might be called *before* the font is ready.

The solution is a **pending queue pattern**:
```js
let _font = null;         // null until font loads
let _pendingGameOver = null;

export function showGameOver(text) {
  if (_font) buildGameOverMesh(text); // ready — build now
  else _pendingGameOver = text;        // not ready — store for later
}

// Inside the font load callback:
if (_pendingGameOver) buildGameOverMesh(_pendingGameOver);
```
The font loader callback checks if something was queued while it was loading and processes it immediately.

**Building the mesh:**
Each character gets its own `TextGeometry` + two materials (front face and sides), colored from `DARK_LETTER_COLORS`. The characters are laid out manually with `xCursor` tracking the X position as each letter is placed. After all letters are placed, the group is centered:
```js
const cx = -(box.max.x - box.min.x) / 2 - box.min.x;
group.children.forEach((m) => { m.position.x += cx; });
```

**Fade-in animation:**
Materials have `transparent: true` and start at `opacity: 0`. Each frame, opacity lerps toward the target:
```js
const step = 1 - Math.exp(-dt * 2.0); // exponential ease — fast at first, slows down
_gameOverOpacity += (_gameOverTarget - _gameOverOpacity) * step;
_gameOverMats.forEach((m) => { m.opacity = _gameOverOpacity; });
```
`1 - Math.exp(-dt * k)` is the standard formula for frame-rate-independent lerping. Using a fixed `0.1` fraction would be faster on high-FPS monitors; the exponential form makes it the same speed regardless of frame rate.

**Responsive scaling:**
On narrow screens the text is scaled down to fit:
```js
const halfW = dist * Math.tan((camera.fov * Math.PI) / 180 / 2) * camera.aspect;
const visibleWidth = halfW * 2;
const s = Math.min(1.2, (visibleWidth * 0.72) / _gameOverNaturalWidth);
_gameOverGroup.scale.setScalar(s);
```
This calculates how wide the camera's view frustum is at the depth of the text, then scales the text to fill 72% of that width, capped at 1.2×.

### The background fade (background.js)

A `_bgTarget` color is maintained separately from `scene.background`. Each frame, the background lerps toward the target:
```js
scene.background.lerp(_bgTarget, Math.min(1, dt * 1.2));
```
When match ends:
```js
_bgTarget.set(0x141425); // dark navy
```
On reset:
```js
_bgTarget.set(dark ? DARK_BG : LIGHT_BG); // back to theme color
```
The `_wasMatchOver` boolean guards against the transition firing every frame — it sets true on the first frame match ends, so the trigger runs exactly once:
```js
if (matchOver && !_wasMatchOver) {
  _wasMatchOver = true;
  _bgTarget.set(0x141425);
  showGameOver(...);
}
```

### Unified title colors
Before this commit, the title had hardcoded purple colors in both light and dark mode. After, both modes use `DARK_LETTER_COLORS` — the same rainbow array as the cube face colors. This made the title match the cube's palette in all themes.

### Key concepts
- **Async font loading** — network request; code that depends on it must handle the "not ready yet" case explicitly
- **Pending queue pattern** — store requests that arrive before a resource is ready; process them in the resource's load callback
- **Exponential lerp** (`1 - Math.exp(-dt * k)`) — frame-rate-independent smooth approach; preferred over a fixed fraction per frame
- **`transparent: true` on materials** — required before `opacity` has any effect in Three.js; without it, opacity changes are ignored
- **`_wasMatchOver` guard** — a common pattern: one-shot boolean to fire logic exactly once when a condition becomes true

### Files touched
- `js/title.js` — `buildGameOverMesh`, `showGameOver`, `hideGameOver`, `resizeGameOver`; opacity animation in `updateTitle`; unified letter colors
- `js/background.js` — `_bgTarget`, `_wasMatchOver`, match-over detection in tick loop; `hideGameOver` on reset/next-round
- `css/style.css` — button styles (holographic glow on Reset/Play)

## 2. Dark Mode as Site Default

**Commit:** `7446876` — feat: dark mode default for new visitors

### What changed
One line in `background.js`:

Before:
```js
const savedTheme = localStorage.getItem("theme");
applyTheme(savedTheme === "dark"); // only dark if explicitly saved as dark
```

After:
```js
const savedTheme = localStorage.getItem("theme");
applyTheme(savedTheme !== "light"); // dark unless explicitly saved as light
```

### Why this is the right way to do it
Changing the default from "light unless saved dark" to "dark unless saved light" means:
- **New visitors** (no saved preference) → get dark mode automatically
- **Existing users who saved dark** → still dark (no change)
- **Existing users who saved light** → still light (their explicit choice is respected)

The key insight is: the *absence* of a preference now means dark, not light. You don't need to migrate anything — just flip the logic.

### Key concepts
- **`localStorage.getItem` returns `null`** when the key doesn't exist — this is a falsy value in JavaScript
- **Opt-out vs opt-in** — "dark unless saved light" is an opt-out model for dark mode; the previous version was opt-in

### Files touched
- `js/background.js` — one-line logic change in theme initialization

## 3. Bug: Sound Not Working on iOS

**Commit:** `f26d0f7` — fix: unlock Web Audio on iOS via touchstart prime

### The symptom
All synthesized sounds (click, thud, match win, etc.) worked in desktop Chrome and Firefox but were completely silent on iOS Safari (iPhone/iPad).

### Root cause: iOS Web Audio restriction
iOS Safari has a strict rule: **the `AudioContext` cannot produce sound until it has been created or resumed inside a direct user gesture handler** (a `click`, `touchstart`, etc.).

The game's `AudioContext` was created lazily — on the first call to `getAudio()`, which happened inside game logic like `makeMove()`. By the time a move is made, the browser's gesture window had already closed. From iOS's perspective: "this audio wasn't started by the user tapping, so I'll block it."

This is a security feature to prevent websites from auto-playing audio without user interaction.

### The fix: prime on first gesture

A new export `primeAudio()` was added to `audio.js`:
```js
export function primeAudio() {
  getAudio(); // creates (and implicitly resumes) the AudioContext
}
```

In `background.js`, listeners are attached to the **first** touch or click on the whole document:
```js
function _primeOnce() {
  primeAudio();
  document.removeEventListener("touchstart", _primeOnce, true);
  document.removeEventListener("click", _primeOnce, true);
}
document.addEventListener("touchstart", _primeOnce, true);
document.addEventListener("click", _primeOnce, true);
```

The third argument `true` is `useCapture` — the listener runs during the *capture phase*, before any other handler, so it fires first no matter what element the user touches.

`removeEventListener` is called immediately after the first fire so the function only runs once and doesn't stay attached for the life of the page.

### Why `touchstart` AND `click`?
- `touchstart` catches mobile taps
- `click` catches desktop clicks
- On desktop, `touchstart` never fires — need `click` as the fallback

### Why this was tricky
- The bug only reproduced on real iOS devices; desktop browsers don't enforce the gesture requirement
- No error was thrown — the `AudioContext` existed but silently produced no output
- The fix had to happen at the document level, not at the individual sound level, because the gesture window closes immediately after the user's touch

### Key concepts
- **Web Audio API restriction on iOS** — `AudioContext` must be created/resumed inside a synchronous user-gesture handler; async handlers (setTimeout, fetch callbacks) don't count
- **Capture phase (`useCapture: true`)** — events travel down from document → target (capture), then back up (bubble); capture listeners run first
- **Self-removing listener** — `removeEventListener` inside the handler so it only fires once; avoids calling `primeAudio` on every tap forever
- **`AudioContext.resume()`** — on some browsers, context starts in `"suspended"` state and needs `.resume()` before it produces output; `getAudio()` handles this by calling `.resume()` if needed

### Files touched
- `js/audio.js` — `primeAudio()` export added
- `js/background.js` — `_primeOnce` function; capture-phase listeners on document

## Concepts Worth Knowing for Interviews

- **Web Audio API** — browser API for synthesizing and playing sounds programmatically; no audio files needed; `AudioContext` is the central object
- **iOS gesture restriction** — audio (and some other APIs) require user interaction before they work; a common gotcha for mobile web apps
- **Capture vs bubble phase** — DOM events travel down (capture) then up (bubble); `addEventListener(event, fn, true)` registers a capture listener that runs before bubble listeners
- **Exponential lerp** — `value += (target - value) * (1 - Math.exp(-dt * k))` — smooth, frame-rate-independent animation; the standard way to animate approach in game loops
- **Pending queue / deferred execution** — when a resource isn't ready yet, store what you wanted to do and run it in the load callback; applies to fonts, images, network data
- **One-shot boolean guard** (`_wasMatchOver`) — detect the moment a condition *becomes* true (the transition), not just that it *is* true; prevents re-firing every frame
