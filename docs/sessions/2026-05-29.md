## 1. GLB Animated Characters

### What we built
Two new animated 3D characters rendered on their own `<canvas>` elements:
- **Greeting character** (`greeting.glb`) — plays on the landing overlay while the game loads
- **Celebration character** (`bro-celeb.glb`) — appears under the winner's score when a match is won

### Why separate canvases?
The landing overlay uses `backdrop-filter: blur()` in CSS. Any canvas *inside* a blurred element
gets blurred too. By giving each character its own `<canvas>` positioned on top of everything,
the character stays sharp regardless of what's behind it.

### How the celebration works
1. Match ends → `showCeleb(winner)` is called
2. The canvas fades in (CSS `opacity` transition)
3. The Three.js `AnimationMixer` plays the clip once (`LoopOnce`)
4. A `setTimeout` fires 1 second before the clip ends to start the fade-out
5. On mobile, the main game canvas dims to 15% opacity so the character pops

### Key concepts
- **GLTFLoader** — Three.js loader for the `.glb` binary format (GL Transmission Format)
- **AnimationMixer** — Three.js class that drives skeletal animations; needs `mixer.update(dt)` called every frame
- **`LoopOnce` + `clampWhenFinished`** — plays animation exactly once and freezes on the last frame instead of snapping back to frame 0
- **Separate WebGLRenderer per character** — each canvas needs its own renderer; they share nothing

### Files touched
- `js/model.js` — new file; landing character renderer
- `js/celeb.js` — new file; celebration character renderer
- `js/background.js` — imports and calls `initModel`, `initCeleb`, `updateModel`, `updateCeleb`
- `css/style.css` — positioning for `#model-canvas` and `#celeb-canvas`
- `index.html` — added `<canvas id="model-canvas">` inside overlay, `<canvas id="celeb-canvas">` at body level
- `sw.js` — bumped cache version to v4

## 2. Bug: Celeb Animation Not Appearing

### The symptom
After deploying, the celebration character never appeared on match win even though the code looked correct.

### Root cause: stale service worker cache
A **service worker** is a background script the browser installs that intercepts all network
requests and can serve them from a local cache. The `cacheFirst` strategy means:
> "If I have a cached copy of this file, return it immediately — don't go to the network."

The old JavaScript files were cached under `tic-trap-toe-v4`. After pushing new code,
the browser's SW was still serving the **old JS** (which had no celebration logic) because
it never went to the network to get the update.

### The fix
Bump `CACHE_NAME` in `sw.js` from `"tic-trap-toe-v4"` to `"tic-trap-toe-v5"`.

When the SW activates with a new cache name, it:
1. Installs itself with the new name
2. On activate, **deletes all caches with a different name** (the old one)
3. Claims all open clients immediately

This forces every user to get fresh JS on their next page load.

### Why this was stubborn
The fix was simple (one string change) but the diagnosis was hard because:
- The game appeared to "work" — it just never triggered the animation
- We couldn't reproduce it in local dev (no SW in dev, or SW was already fresh)
- The error was invisible — no console errors, the code just silently served stale files

### Lesson
Any time a deployed change doesn't appear but local dev looks fine, **suspect the service worker cache first**. Bump the version string to bust it.

### Files touched
- `sw.js` — `CACHE_NAME` string changed

## 3. Bug: Dark Mode Not Default on Mobile Web / Desktop

### The symptom
Dark mode was the intended default, but users on mobile web and desktop saw a **flash of light mode** on every page load, sometimes staying in light mode entirely.

### Why it happened — three separate causes

This was a multi-layer bug, which is why it was stubborn. Each fix alone was not enough.

#### Layer 1: CSS Flash of Unstyled Content (FOUC)
JavaScript loads **after** the browser has already painted the page once.
The `<body>` had no class, so CSS dark styles never applied until JS ran and added `class="dark"`.

**Fix:** Add `class="dark"` directly to `<body>` in `index.html`.
```html
<body class="dark">
```
Now the very first paint is already dark. No JS needed for the initial style.

#### Layer 2: Three.js scene was always initialized light
Even after the CSS fix, the Three.js `WebGLRenderer` canvas (which covers the whole background)
was initialized with `scene.background = LIGHT_BG` — a hardcoded light color — before reading
`localStorage`. So the canvas flashed white before the theme check ran.

**Fix:** Read `localStorage` *before* creating the scene, then initialize `scene.background`
to the correct color from frame one.
```js
const _initialDark = localStorage.getItem("theme_v2") !== "light";
scene.background = new THREE.Color(_initialDark ? DARK_BG : LIGHT_BG);
```

#### Layer 3: Old users had "light" saved in localStorage
The `localStorage` key was `"theme"`. Before dark mode became the default, some users had
`localStorage.getItem("theme") === "light"` saved. Even after the CSS and scene fixes,
those users would read their saved preference and switch to light mode.

**Fix:** Rename the key from `"theme"` to `"theme_v2"`. Any user without an explicit new
preference gets `null` back from `getItem("theme_v2")`, which we treat as dark.
```js
const saved = localStorage.getItem("theme_v2"); // new key — old "light" pref is gone
const isDark = saved !== "light"; // null → dark (the new default)
```

### Why this was stubborn
Three independent causes, each partially masking the others. Fixing one didn't fix all three.
The order mattered: FOUC → scene init → localStorage key.

### Key concepts
- **FOUC (Flash of Unstyled Content)** — a brief moment where the browser renders HTML before CSS is applied; solved by inlining critical styles or setting classes in HTML before JS runs
- **`localStorage`** — browser key-value store that persists across page reloads; `getItem` returns `null` if the key doesn't exist
- **Key versioning** — a standard technique: when you need to invalidate a stored user preference, rename the key rather than delete it

### Files touched
- `index.html` — `<body class="dark">`
- `js/background.js` — read `localStorage` before scene init; `theme_v2` key

## 4. Y-Axis Cube Steering Toward Remaining Faces

### The feature
When 1 or 2 side faces (front/back/left/right) remain unfinished, the cube's Y rotation
biases toward those faces instead of spinning equally through all 6.

### Why
Players were waiting a long time for the cube to naturally drift back to the one face they
still needed to win. The cube was fair to all faces, including already-won ones.

### How it works
Each face has a `NORMALS[fi]` vector — a direction pointing outward from that face.
To find what Y rotation angle would bring a face to the front:
```js
const idealY = -Math.atan2(NORMALS[fi].x, NORMALS[fi].z);
```
`Math.atan2` converts a direction vector into an angle. Negated because rotation and
direction are in opposite coordinate senses.

The rotation velocity gets a `tanh`-shaped nudge toward that angle:
```js
const err = wrappedAngleDiff(idealY, rotY);
rotVelY += steeringStrength * Math.tanh(err * 0.8) * dt;
```
`tanh` is used instead of raw `err` so the nudge saturates — it doesn't go infinite
when the face is far away. The cube still spins naturally; it just spins faster toward
the needed face.

### Key concepts
- **Normal vector** — a unit vector pointing perpendicular to a surface; used everywhere in 3D math
- **`Math.atan2(y, x)`** — converts a 2D direction into an angle; more reliable than `Math.atan` because it handles all quadrants
- **Angle wrapping** — angles can be 0° or 360° (same direction) so you must normalize to `[-π, π]` before arithmetic: `((err % 2π) + 3π) % 2π - π`
- **`Math.tanh`** — a smooth S-curve that clamps output to `[-1, 1]`; good for velocity nudges that shouldn't blow up

### Files touched
- `js/cube.js` — rotation block; `NORMALS` array; steering velocity calculation

## 5. Tiered Rotation System (Spring-Lock)

### The feature
Three behavior tiers based on how many faces remain:

| Remaining faces | Tier | Behavior |
|---|---|---|
| 3+ | 1 | Natural continuous spin, mild bias |
| 2 | 2 | 2× speed, steers between the two |
| 1 | 3 | Spring-locks onto that face with gentle breathing idle |

### Why
Tier 3 is the end-game moment. It would feel anticlimactic if the cube kept drifting aimlessly
when there's only one face left to win. Locking it creates tension and focus.

### How spring-locking works (Tier 3)
A **spring** is a physics model: if you pull a mass on a spring, it accelerates toward rest.
The equation is:
```
acceleration = spring_stiffness × error − damping × velocity
```
In code:
```js
const errY = wrappedAngleDiff(idealY, rotY);
rotVelY += (errY * 3.0 - rotVelY * 4.5) * dt;
rotY += rotVelY * dt;
```
- `3.0` is the spring constant (stiffness — how hard it pulls)
- `4.5` is the damping (friction — how fast it slows down)
- When damping is high enough relative to stiffness (`ζ > 1`), the spring is **overdamped** — it settles smoothly without bouncing

The `_lockBlend` variable (0 → 1) transitions smoothly between free spin and spring-locked behavior over ~0.67 seconds so the lock-on isn't a jarring snap.

### Breathing idle
When fully locked, a gentle sine wave wobbles the position:
```js
const breathY = Math.sin(t * 0.31) * 0.06 * _lockBlend;
cube.rotation.y = rotY + breathY;
```
This makes the cube feel alive rather than frozen.

### Key concepts
- **Spring physics** — position/velocity system; used constantly in animation, UI, and game feel
- **Damping ratio (ζ)** — `ζ < 1` = bouncy (underdamped), `ζ = 1` = perfect settle (critically damped), `ζ > 1` = slow no-bounce settle (overdamped)
- **`Math.sin` for idle motion** — a pure sine wave creates a smooth back-and-forth; multiplying two sines at different frequencies creates organic-feeling motion
- **Blend factor** — a value from 0 to 1 that linearly interpolates between two behaviors; lerping it toward a target each frame gives smooth transitions

### Files touched
- `js/cube.js` — entire rotation block rewritten with 3-tier logic; `_lockBlend` variable added; `xOffset` for X-axis locking

## 6. Game-Over Text Position

### The feature
When a match ends, the "X WINS!" / "O WINS!" / "DRAW!" text now appears at `y = 10`
(where the title floats) instead of `y = 5` (in front of the cube). The title hides when
game-over text is shown, and reappears on reset.

### Why
At `y = 5` the text was cluttered in the same visual space as the cube, making both harder
to read. Moving it to the title position creates a clean visual swap — one thing at a time.

### How
`title.js` manages both the title mesh and the game-over group as separate Three.js objects.
```js
titleMesh.visible = false;        // hide title
_gameOverGroup.position.y = 10;   // same Y as title
_gameOverGroup.rotation.x = 0.22; // same tilt as title
```
On reset:
```js
titleMesh.visible = true;
hideGameOver();
```

The scale is responsive — on narrow screens the text shrinks to fit:
```js
const scale = Math.min(1.0, (visibleWidth * 0.88) / _gameOverNaturalWidth);
```

### Key concepts
- **Mesh visibility** — `mesh.visible = false` keeps the object in the scene but skips rendering it; cheaper than removing and re-adding it
- **Scene graph** — Three.js organizes objects in a hierarchy; a `Group` can contain multiple meshes and be moved/rotated as a unit
- **`lookAt`** — makes an object always face the camera; used here so the text stays readable as the cube rotates behind it

### Files touched
- `js/title.js` — game-over group moved to y=10; title visibility toggling; responsive scale

## 7. Light Mode Cat on Landing Page (Dual Characters)

### The feature
Light mode gets a cat character (`greeting-light.glb`) on the landing page.
Dark mode keeps the existing bro (`greeting.glb`).
Toggling the theme swaps them instantly — no reload, no re-fetch.

A second dual-character system was added for the celebration: `white-celeb.glb` for light mode
alongside the existing `bro-celeb.glb` for dark.

### Why load both at startup (original approach)
The idea was instant theme switching: pre-load both, hide the inactive one, swap visibility on toggle.
No latency when the user switches.

### Why this was later changed (lazy loading — see section 9)
Loading both at startup meant 13.9 MB of GLB data downloaded and cached on every page load,
even if the user never toggles the theme. The better tradeoff is: load only the active one,
load the other on first toggle (accepting a brief load delay that time only).

### Key concept: Draco compression
GLB files can be large. Draco is a geometry compression library from Google.
`DRACOLoader` decompresses the file in a Web Worker (off the main thread) as it arrives.
Without it, the file would be larger and decompression would block the render loop.
```js
const draco = new DRACOLoader();
draco.setDecoderPath("https://unpkg.com/three@0.160.0/examples/jsm/libs/draco/");
const loader = new GLTFLoader();
loader.setDRACOLoader(draco); // attach to GLTFLoader before calling .load()
```

### Landing theme toggle
The `#landing-theme-toggle` button was added inside the `#landing-overlay` so users can
switch theme before clicking Play — previously the toggle was only accessible after dismissing the overlay.

### Files touched
- `js/model.js` — dual character loading; `setDarkMode` swap logic
- `js/celeb.js` — dual character loading; light celeb support
- `js/background.js` — calls `setModelDark`, `setCelebDark` from `applyTheme`
- `index.html` — `#landing-theme-toggle` button added to overlay

### Why this matters
- **Co-location** — each component's CSS lives next to its JS; you never search for where a style is defined
- **Single responsibility** — `base.css` is layout; `dark.css` is theme; each component owns its own styles
- **`public/`** — static assets served as-is; separating them from source code makes it clear what's "built" vs "shipped raw"

### How the CSS was split
The original `css/style.css` was 1068 lines. It was read in full, then each block of rules
was moved to the file that owns it. The rule: "if this CSS only affects elements inside component X, it belongs in X's CSS file."

### What git mv does
Using `git mv old-path new-path` instead of just moving files preserves git history.
The file's commit log follows it to the new location. Without it, git sees a delete + add,
and `git log` on the new file starts empty.

### Files touched
- Everything. 45 files changed. All JS moved to `src/`. `css/style.css` deleted and split into 9 files.
  All assets moved to `public/`. `sw.js` updated to reference new paths. `index.html` updated with 9 CSS link tags.

## 9. Performance: Lazy-Load GLBs + Service Worker Cache Fix

### The problem
DevTools showed **28.9 MB** in cache storage after a single page load.

Breakdown:
- `greeting.glb` — 6.6 MB (dark landing character)
- `greeting-light.glb` — 7.3 MB (light landing character)
- `bro-celeb.glb` — 6.6 MB (dark celebration)
- `white-celeb.glb` — 6.9 MB (light celebration)
- Total GLBs: **27.4 MB**

All four were loaded at startup. The service worker's `cacheFirst` strategy was also storing
all four in the SW cache — so they were in **two** places: browser HTTP cache + SW cache.

### Fix 1: Lazy-load inactive theme characters
Only load the GLB for the current theme. Load the other on first theme toggle.

```js
// initModel() — only load active theme
const activeKey = _isDark ? "dark" : "light";
const activePath = _isDark
  ? "/public/models/greeting.glb"
  : "/public/models/greeting-light.glb";
_loadChar(activeKey, activePath);

// setDarkMode() — lazy-load on first toggle
if (!_chars[newKey]) {
  _loadChar(newKey, newPath);
}
```

Same pattern applied to `celeb.js`.

### Fix 2: Exclude model files from SW cache
The SW's `cacheFirst` handler was fetching and storing every local file it encountered.
Added a passthrough for `/public/models/`:

```js
// In fetch event handler:
if (url.pathname.startsWith("/public/models/")) return; // let browser HTTP cache handle it
```

The browser's built-in HTTP cache (controlled by `Cache-Control` headers) is already
well-suited for large static binary files. The SW's job is to make the *game* work offline —
the decorative models are not needed for that.

### Fix 3: Also fixed the pending trigger bug in celeb.js
The original `showCeleb` waited for **both** dark and light characters to finish loading
before triggering. Since we now only load one at startup, this would wait forever.
Fixed to check only the active character:
```js
// After load completes:
if (_pendingWinner && charObj === _char()) { // _char() returns the active one
  _trigger(_pendingWinner);
  _pendingWinner = null;
}
```

### Result
Cache storage drops from **~29 MB to ~2 MB** on a fresh page load.
Only one ~7 MB GLB is fetched at startup instead of four.

### Key concepts
- **Service worker cache vs browser HTTP cache** — two different caches. The SW cache (`caches.open`) is controlled by your JS. The HTTP cache is controlled by `Cache-Control` response headers set by the server. Large static files belong in HTTP cache (the server handles expiry); small critical JS belongs in SW cache (you control offline behavior).
- **`cacheFirst` strategy** — check SW cache first, fall back to network; fast but can serve stale files (hence version bumping)
- **`networkFirst` strategy** — go to network first, fall back to cache; always fresh when online; used for external CDN resources
- **Lazy loading** — load resources only when needed; the tradeoff is a delay on first use vs. wasted bytes if never used

### Files touched

- `src/components/model/model.js` — lazy-load logic in `initModel` and `setDarkMode`
- `src/components/celeb/celeb.js` — lazy-load logic; fixed pending trigger check

## Concepts Worth Knowing for Interviews

- **Service workers** — background scripts that intercept fetch requests; enable offline PWAs; `cacheFirst` vs `networkFirst` strategies
- **FOUC** — flash of unstyled content; fixed with inline HTML classes or synchronous CSS
- **localStorage key versioning** — when preferences change format, rename the key rather than migrate
- **Spring physics** — stiffness × error − damping × velocity; overdamped = no bounce
- **GLTFLoader + DRACOLoader** — Three.js asset pipeline; Draco compression is optional but critical for large models
- **AnimationMixer** — Three.js animation driver; must call `.update(dt)` every frame
- **Lazy loading** — defer expensive work until it's actually needed; accept first-use latency in exchange for startup savings
- **Co-located CSS** — styles live next to the component they style; easier to find, easier to delete when the component goes away
- **`git mv`** — moves a file and preserves its git history; plain `mv` + `git add` loses the log
