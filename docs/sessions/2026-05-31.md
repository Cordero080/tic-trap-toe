## Bug 1 — "X WINS!" text was completely invisible

**Symptom:** After winning a match, the 3D win text never appeared. The title just disappeared and nothing replaced it.

**Files:** `src/components/title/title.js`

**Root cause:** A space character (`" "`) in the string `"X WINS!"` was being passed to Three.js `TextGeometry`, which builds 3D letter meshes from font data. Space has no geometry (it's just air), so Three.js returned an empty bounding box — a box with no size. In math terms, its `max` was `-Infinity` and its `min` was `+Infinity`.

The code then calculated the letter width as `max - min = -Infinity`. That poisoned `xCursor` (the variable tracking horizontal position) for every letter that followed, giving them all positions of `-Infinity`. The bounding box of the whole group came out as `-Infinity` wide, so the scale calculation divided by `-Infinity` and got effectively zero. The text was scaled to nothing.

**The fix:** Special-case the space character — skip creating geometry for it, manually advance the cursor by a fixed amount, and move on.

```js
if (ch === " ") {
  xCursor += 1.2;
  colorIdx++;
  continue;
}
```

**Lesson:** `TextGeometry` does not handle whitespace. Always validate that geometry actually has vertices before using its bounding box. `-Infinity` in a bounding box is a signal that the geometry is empty.

**Key term — Bounding box:** An invisible box that wraps around a 3D object, used to measure its size and position. Three.js computes these automatically, but only if the object has actual geometry.

## Bug 2 — Cube rotation was oscillating and freezing on completed faces

**Symptom:** The cube would spin toward a completed (already won) face, slow down, reverse direction, then spin back. It would oscillate back and forth instead of moving toward unfinished faces. Sometimes it froze entirely.

**Files:** `src/components/cube/cube.js`

**Root cause (part 1 — direction reversal):** The rotation code used `Math.sign(Math.sin(t * 0.09))` to decide which direction to spin. `Math.sin` is a wave that goes positive and negative on a cycle — so every ~35 seconds the sign flipped, reversing the cube's direction mid-game with no relation to game state.

**Root cause (part 2 — oscillation at midpoint):** When 2 active faces remained, the code computed the angular distance to each face and spun toward the nearest one. At the exact midpoint between two faces, both had equal distance. The code would pick one, overshoot slightly, then on the next frame pick the other, overshoot back — bouncing forever.

**The fix:** Throw away all direction/distance math. Instead, check which face is currently pointing toward the camera (using the cube's rotation quaternion to transform each face's normal vector into world space). If that face is complete, speed up. If it's active, slow down. Direction never reverses — the cube only ever moves forward.

```js
// Which side face is currently facing the camera?
let maxCamZ = -Infinity;
let facingFi = 0;
for (const fi of [0, 1, 4, 5]) {
  _tmpN.copy(NORMALS[fi]).applyQuaternion(cube.quaternion);
  if (_tmpN.z > maxCamZ) { maxCamZ = _tmpN.z; facingFi = fi; }
}
const targetVel = faceStates[facingFi].winner ? FAST : SLOW;
```

**Lesson:** When steering logic uses a time-based wave (`Math.sin(t)`) to decide direction, it will eventually reverse regardless of what the game state says. Game logic and animation timing must be decoupled. Oscillation bugs are almost always caused by the correction mechanism overshooting and correcting in the wrong direction — simplify the logic until there's no "correction," just a target.

**Key terms:**
- **Quaternion:** A mathematical way to represent 3D rotation that avoids common problems like gimbal lock. Used internally by Three.js.
- **Normal vector:** A vector (arrow) pointing perpendicular to a surface — used here to know which direction each cube face is "pointing."
- **`applyQuaternion`:** Rotates a vector by the cube's current orientation to get the world-space direction.

## Bug 3 — Win text invisible on mobile behind the celebration animation

**Symptom:** On mobile, after winning a match, the "X WINS!" 3D text was nearly invisible. The celebration character appeared but the text was barely visible behind it.

**Files:** `src/components/celeb/celeb.js`, `src/components/title/title.js`, `index.html`, `src/styles/base.css`

**Root cause:** This was a **multi-canvas layering problem**. The game uses two separate HTML `<canvas>` elements:
- `bg-canvas` — the main Three.js scene (cube + win text)
- `celeb-canvas` — the celebration character

On mobile, the code set `bg-canvas` opacity to `0.15` to dim the cube so the character would visually "pop" in front of it. But the "X WINS!" text lives on `bg-canvas` too — dimming the canvas dimmed everything on it, including the text.

**Why the obvious fix didn't work:** The first attempt was to add a DOM overlay `<div>` with the win text. But `<div>` elements don't know the 3D camera position, so the text appeared in the center of the screen overlapping the cube instead of at the top where the 3D title normally sits.

**The actual fix:** Create a third canvas (`win-canvas`) with its own Three.js renderer and scene. Move the win text group into this separate scene. Now the layer order is:

```
bg-canvas    (z-index: -1)  — cube only — can be dimmed freely
celeb-dim    (z-index:  5)  — a dark <div> overlay shown on mobile
win-canvas   (z-index: 10)  — win text only — never dimmed
celeb-canvas (z-index: 150) — celebration character
```

The cube dims, the character appears over it, and the win text sits above the dim on its own canvas.

**Lesson:** When multiple visual elements share a canvas, you can't style them independently with CSS — CSS opacity, filters, and z-index apply to the canvas element as a whole. If you need independent layering of 3D content, you need independent renderers. This is a common problem in Three.js and WebGL generally.

**Key terms:**
- **Canvas:** An HTML element that JavaScript can draw into programmatically. Three.js renders everything to a canvas.
- **z-index:** A CSS property that controls which element appears "in front" when elements overlap. Higher number = in front.
- **Renderer:** The Three.js object responsible for drawing a scene to a canvas. Each canvas needs its own renderer.
- **Opacity:** How transparent something is. 0 = invisible, 1 = fully visible, 0.15 = nearly transparent.

## Bug 4 — Celebration animation auto-dismissed before user could read the result

**Symptom:** The celebration character faded out on its own after the animation clip finished. Users didn't realize they could click Next Round because the character disappeared and buttons were hidden behind the dim overlay.

**Files:** `src/components/celeb/celeb.js`, `src/components/hud/hud.css`, `src/components/cube/cube.css`

**Root cause (part 1 — auto-fade):** A `setTimeout` fired `(clipDuration - 1) * 1000` milliseconds after the animation started, calling `_fadeOut()`. This dismissed the character regardless of what the user was doing.

**Root cause (part 2 — buttons hidden):** The dark dim overlay (`#celeb-dim`) was at `z-index: 5`. The score bar, buttons, and message had no explicit `z-index`, which in CSS means they render below any element with a positive z-index. So the dim covered them.

**Key term — z-index stacking:** In CSS, positioned elements with no explicit `z-index` are treated as `z-index: 0` and sit below any element with a positive z-index. Setting `z-index: 20` on the HUD elements put them above the dim at `z-index: 5`.

**The fix (auto-fade):** Remove the `setTimeout`. The animation plays once and holds on the last frame (`clampWhenFinished = true` in Three.js). `hideCeleb()` is called explicitly when the user clicks Next Round.

**The fix (hidden buttons):** Add `z-index: 20` to `.controls`, `.score-bar`, `.round-label`, and `h2`.

**Lesson:** Never assume UI elements are "above" an overlay just because they appear later in the HTML. Always set explicit z-index values when layers matter. And whenever you add an auto-dismiss timer to UI, ask: does the user have time to read and act on this?

## Bug 5 — Light mode character looked flat white with no depth

**Symptom:** The white cat character (light mode) looked completely washed out — no shadows, no depth, indistinguishable from the background.

**Files:** `src/components/model/model.js`, `src/components/celeb/celeb.js`

**Root cause:** The scene lighting was tuned for the dark character and applied equally to both. `AmbientLight` at intensity `0.7` (ambient = light that comes from everywhere equally, casting no shadows) plus a `DirectionalLight` at `1.4` (white) meant the white cat was receiving so much light from all directions that there were no dark areas — no shadows, no depth, no sense of volume.

**The fix:** In light mode, drop the ambient to `0.15` and switch to a warm key light + cool fill + rim light scheme:

- **Ambient light** (`0.15`) — very low so shadow areas are actually dark
- **Key light** — warm yellow-white (`0xfff3d0`), intensity `2.2`, from upper-right — the "sun"
- **Fill light** — cool blue (`0x7799cc`), intensity `0.6`, from the left — simulates sky bounce
- **Rim light** — white, intensity `0.7`, from behind — separates the silhouette from the background

This is called **three-point lighting** — a technique from photography and film that creates the illusion of 3D volume using just three light sources.

Both `model.js` (landing page character) and `celeb.js` (match-win character) had the same bug and received the same fix. Light settings are stored in a `_lights` object and updated when the theme changes via `_applyLightMode(dark)`.

**Lesson:** Ambient light is the enemy of depth. High ambient = flat. Real depth comes from contrast between lit and unlit surfaces. When a character looks flat, the first thing to check is ambient intensity.

**Key terms:**
- **Ambient light:** Light with no direction — illuminates everything equally. Real rooms have some ambient (light bouncing off walls), but too much kills shadows.
- **Directional light:** Light coming from one direction, like the sun. Creates clear shadows and defines volume.
- **Three-point lighting:** A classic lighting setup with a key (main) light, a fill (shadow-side) light, and a rim (back-edge) light.

## Bug 6 — Service worker caching forced a manual version bump after every deploy

**Symptom:** After every code change, users with the site cached saw the old version. The workaround was bumping a version string (`v17` → `v18` → ...) every commit to force cache invalidation.

**Files:** `sw.js`

**Root cause:** The service worker used a **cache-first** strategy for all local files: serve from local cache, only hit the network if the file isn't cached yet. Once cached, a file is served from local storage forever — the server is never asked for an update.

**The fix:** Switch JS and CSS files to **network-first**: always try the network first, fall back to cache if offline. The server responds with a `304 Not Modified` (a tiny header-only response) if the file hasn't changed, so the browser just uses the cached copy — no re-download. If the file changed, the fresh version comes down.

HTML, icons, and manifest stay cache-first since they almost never change and you want the fastest possible shell load.

```js
const isCode = p.endsWith(".js") || p.endsWith(".css");
event.respondWith(isCode ? networkFirst(event.request) : cacheFirst(event.request));
```

**Lesson:** Cache-first is fast but stale. Network-first is always fresh but requires a network round-trip. Choose based on how often the file changes — use cache-first for truly static assets (icons, fonts), network-first for code that deploys frequently. The performance cost of network-first on small JS files is negligible compared to the cost of users running stale code.

**Key terms:**
- **Service worker:** A background script the browser runs separately from the page. It intercepts network requests and can serve cached responses.
- **Cache-first:** Check local cache first. Fast, but stale after deploys.
- **Network-first:** Check the server first. Always fresh, tiny delay.
- **304 Not Modified:** An HTTP response code meaning "the file hasn't changed, use your cached copy." Only the response headers are sent — not the file itself. Very fast.
- **Cache invalidation:** The process of telling a cache that its stored copy is outdated. Widely considered one of the hardest problems in software.
